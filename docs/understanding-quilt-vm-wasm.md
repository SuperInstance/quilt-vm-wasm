# Understanding quilt-vm-wasm

Everything here was checked against the code at commit `001fa53` (`src/lib.rs`, `Cargo.toml`, `www/index.html`). Commands were run in a Linux container with Rust and `wasm32-unknown-unknown` installed. `wasm-pack` and the `wasm-bindgen` CLI were **not** installed, so nothing below claims the JavaScript glue was generated or run in a browser.

## 1. In one breath

`quilt-vm-wasm` is one ~250-line Rust file (`src/lib.rs`) that implements a tiny in-memory "cell graph" with five operations — `bind`, `link`, `effect`, `view`, `tick` — and, when built with the `wasm` feature for `wasm32`, exposes them to JavaScript as a `WasmQuiltVM` class.

## 2. Why it exists

The wider "Quilt" project family (see the README) defines the same five operations in several languages. This repo is the WebAssembly member: it lets a browser page or a Node script create a VM, record cells and relations, and read them back, without a server. Functionally it is a small, serializable record-keeper: it stores named JSON values, typed edges between names, and logs of what was asked of it.

It is deliberately honest to say what it is **not**: see §5 and §6. It does not execute effects, evaluate formulas, or enforce immutability or access control. The README's prose about spreadsheets, TTRPGs and neural nets describes the intended vocabulary, not behaviour present in this code.

## 3. The mental model

- **QuiltVM** (`src/lib.rs`, `pub struct QuiltVM`): the whole state. Plain data: `cells`, `links`, `effects`, `views`, `ticks`, `time`. It derives `Serialize`/`Deserialize`/`Default`, so a VM can be dumped to JSON.
- **Cell**: `{name, value: serde_json::Value, immutable: bool}`, stored in a `BTreeMap` keyed by name. Created by `bind`. `immutable` is always set to `true` but nothing reads it.
- **Link**: `{a, b, relation, weight}` — a directed, typed edge from name `a` to name `b`, appended to a `Vec`. `weight` is always `1.0`. Endpoints are not checked against `cells`.
- **Records** (`EffectRecord`, `ViewRecord`, `TickRecord`): append-only logs. `effect` stores a forward name and an inverse name as *strings*; `view` logs who looked at what; `tick` logs `dt` and the resulting clock.
- **The boundary**: `WasmQuiltVM` (module `wasm_bindings`) is a newtype around `QuiltVM`. It converts JS values to `serde_json::Value` on the way in and back with `serde_wasm_bindgen` on the way out. All logic stays in `QuiltVM`.

## 4. Walkthrough

### What runs where

| Where | What | Gate |
|---|---|---|
| Any target | `QuiltVM` and the five methods, plus `stats()` and `reachable()` | always compiled |
| Any target (test builds) | 5 unit tests in `mod tests` | `#[cfg(test)]` |
| `wasm32` **and** feature `wasm` | `WasmQuiltVM` JS-facing class | `#[cfg(all(target_arch = "wasm32", feature = "wasm"))]` |

The browser page `www/index.html` imports `./quilt_vm_wasm.js` and calls `new WasmQuiltVM()`; that JS file is generated by `wasm-bindgen`/`wasm-pack`, it is not in the repo.

### Run a quilt natively

A scratch crate outside the repo (path dependency on it) ran this sequence:

```rust
let mut vm = QuiltVM::new();
vm.bind("A1", json!(10));  vm.bind("A2", json!(20));  vm.bind("B1", json!(0));
vm.link("B1", "A1", "depends_on");  vm.link("B1", "A2", "depends_on");
vm.effect("B1", "inc", "dec");
vm.view("A1", "anyone");  vm.view("nope", "anyone");
vm.tick(1.0);  vm.tick(2.5);
vm.reachable("B1", Some("depends_on"));   vm.reachable("A1", Some("depends_on"));
vm.bind("A1", json!(99));                  // rebind
vm.link("B1", "ghost", "depends_on");      // dangling target
```

Actual output:

```
view A1 = Some(Number(10))
view nope = None
reachable B1 depends_on = ["A1", "A2", "B1"]
reachable A1 depends_on = ["A1"]
rebind A1 = Number(99), n_cells=3
dangling: ["A1", "A2", "B1", "ghost"]
stats = {"n_cells":3,"n_effects":1,"n_links":3,"n_ticks":2,"n_views":2,"time":3.5}
```

Read it as: a "formula" (B1 depends on A1, A2) is just edges; `reachable` walks them (depth-first, result sorted, includes the start). Nothing computed `B1 = A1 + A2`. Note that `view("nope")` returned nothing but **still incremented `n_views`**.

### Cross the VM/WASM boundary

`cargo build --target wasm32-unknown-unknown --features wasm --release` succeeds and yields `target/wasm32-unknown-unknown/release/quilt_vm_wasm.wasm`. Listing its exports from Node includes `wasmquiltvm_new_…`, `_bind_…`, `_link_…`, `_effect_…`, `_view_…`, `_tick_…`, `_time_…`, `_stats_…`, `_reachable_…` and `__wbg_wasmquiltvm_free_…` (the hash suffix is generated). Without `--features wasm` the exports are only `memory`, `__data_end`, `__heap_base`. That is the boundary: the feature decides whether JS can see the VM at all.

## 5. The contract

- **Inputs**: `bind(name, value)` — any JSON-representable value; on the JS side a value that `serde_wasm_bindgen` cannot convert returns an error (`Result<(), JsValue>`). `link(a, b, relation)`, `effect(target, forward, inverse)`, `view(target, viewer)`, `tick(dt)` take strings / `f64`.
- **Outputs**: `view` returns the cell's *value* only (JS `null` if missing; native returns `Option<&Cell>`). `time()` returns the clock. `stats()` returns counts plus `time`. `reachable(start, relation)` returns a sorted array of names; an empty `relation` string means "any relation" on the JS side.
- **Invariants that actually hold** (from code and tests): names are unique keys (rebinding overwrites — verified above); `time` is the sum of all `dt` (test `tick_advances_time`: 1.0 then 2.5 gives 3.5); every `view`/`tick`/`effect`/`link` call appends exactly one record; `reachable` always contains `start`.
- **Invariants that do NOT hold**: `immutable` is never enforced; `dt` is not validated (negative or NaN would be accepted — from reading the code, not run); links may dangle; effects are never applied or reversed; `viewer` does not affect what is returned.
- **Receipt**: there is no signed or hashed receipt. The closest thing is the whole `QuiltVM` state, serializable via `serde_json::to_string(&vm)` (run above; output starts `{"cells":{"A1":{"name":"A1","value":99,"immutable":true}…`), and `stats()` as a quick summary.

## 6. Failure modes and scars

- **`wasm-pack build --target web` alone likely exports nothing.** `default = []` in `Cargo.toml`, and the bindings need `feature = "wasm"`. The README command omits it; pass `-- --features wasm`. Verified indirectly: the plain wasm32 build exports no `WasmQuiltVM`. (I did not run `wasm-pack` itself.)
- **Demo page path mismatch.** `www/index.html` imports `./quilt_vm_wasm.js`, but `wasm-pack` writes to `pkg/`, and the README serves `www/`. You must copy or symlink the `pkg/` contents into `www/`. Not run in a browser.
- **`stats()` from JS.** The source comment on `time()` says `stats()` returns empty objects due to a serde-wasm-bindgen serialization problem; `time()` was added as a scalar workaround (commit `a0031d1`). I could not reproduce it (no JS glue); a plausible cause is that `serde_json::Value` objects become JS `Map`s, which `JSON.stringify` prints as `{}` — unverified. `www/index.html` still does `JSON.stringify({stats,…})`, so it may show empty stats.
- **Manifest history**: commit `82610a4` fixed `wasm-bindgen` being referenced by a feature but not optional. Note `js-sys` is still an unconditional wasm32 dependency, so it inflates the un-featured wasm too.
- **`view` mutates.** It takes `&mut self` because it logs; a "read" changes state and `n_views`.
- **Docs vs. code.** README claims (per-op nanoseconds, "~5ms gold demo", 8 polyformalisms, `projection="formatted"`, subscribers, GC on tick) are not backed by code or benchmarks in this repo. `vm.view(name, viewer)` takes no projection argument.
- **No `.gitignore`**: `cargo build` leaves untracked `target/` and `Cargo.lock`.

## 7. How it composes

- With JS: construct, call methods, read results; state lives in wasm linear memory and is freed via the generated `free()`.
- With Rust: depend on the crate as an `rlib` (`crate-type = ["cdylib","rlib"]`) and use `QuiltVM` directly, as the scratch program did.
- With sibling repos (quilt-vm-typescript etc.): same opcode names; I did not inspect those repos, so any behavioural equivalence is unverified.
- Persistence: `QuiltVM` is `Serialize`/`Deserialize`, so state can be stored as JSON; `WasmQuiltVM` does not expose that.
